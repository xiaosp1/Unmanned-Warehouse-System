# WorkBuddy 项目 · 多人协作落地指南

> 目标：把本地目录 `D:\01-DEMO\Unmanned Warehouse System` 变成**团队成员都能接手维护**的项目，
> 而不是"只有一台电脑上有最新版"的单机工作区。

---

## 0. 先说结论

多人维护不是"把文件夹共享出去"就完事。它需要**三条线同时成立**，缺任何一条都会回到"互相覆盖、版本混乱"：

| 线 | 解决什么 | 用什么 |
| --- | --- | --- |
| **代码层** | 源码谁改了什么、能不能回滚 | Git 仓库（`main` 保护 + 短分支 + PR 评审） |
| **资产层** | 大文件、设计稿、现场素材放哪 | 项目网盘（不进 Git） |
| **过程层** | 谁在做什么、卡在哪、谁负责 | 项目待办 + 项目消息 |

三层的关系：

```
        项目待办（任务从哪来、谁负责）
                 │
                 ▼
   短分支开发 ──► PR 评审 ──► main（唯一真相）
                 │
                 ▼
        项目网盘（大文件与交付物的家）
```

## 1. 七步落地

### 第 1 步：把本地目录变成 Git 仓库

本仓库已经内置好脚手架（`.gitignore`、`.gitattributes`、`CODEOWNERS`、PR/Issue 模板、规范文档）。
在 `D:\01-DEMO\Unmanned Warehouse System` 下执行：

```powershell
# Windows PowerShell
powershell -ExecutionPolicy Bypass -File scripts\init-repo.ps1
```

脚本会做四件事：初始化仓库（`main` 分支）、写入本地 git 配置（换行/长路径/提交模板/拉取用 rebase）、
检查提交身份、生成首个提交。

> ⚠️ 如果目录里已经有一堆文件，首个提交会是"全量入库"。
> **提交前务必确认 `.env`、现场账号、真实数据没有被 `git add` 进去**（`.gitignore` 已覆盖常见情况）。

### 第 2 步：建远端仓库并推送

选一个团队已经在用的平台（GitHub / Gitee / 工蜂），新建**空仓库**（不要勾选初始化 README），然后：

```bash
git remote add origin <仓库地址>
git push -u origin main
```

推送后立刻去平台设置里做三件事：

1. **保护 `main`**：禁止直推、禁止 force push、要求 PR + 至少 1 人 approve、要求 CI 通过
2. **配置评审人**：GitHub / 工蜂 读 `CODEOWNERS`；Gitee 需在页面上手工指定
3. **关掉无关的自动合并**，合并方式统一用 **squash**

### 第 3 步：在 WorkBuddy 项目里挂上它

项目工作空间指向这个仓库（或直接以该仓库为项目根目录打开）。

> 入口名称各版本略有差异，一般在「项目设置 → 工作空间 / 代码仓库」。
> 判断标准很简单：**在这个项目里新建的 Agent 会话，能直接看到仓库文件并提交**。

此时要确认一件事：**团队每个人看到的是同一份代码**。
如果你本地 `D:\` 下的目录和项目工作空间不是同一个，说明还没打通 —— 要么把项目工作空间指到该目录，
要么让所有人改为从远端 `clone`。

### 第 4 步：把成员拉进来

「项目设置 → 成员」里邀请，角色按下面给：

| 角色 | 给谁 | 能做什么 |
| --- | --- | --- |
| `project.owner` 所有者 | 1–2 人，项目负责人 + 技术负责人 | 改项目设置、增删成员、删项目 |
| `project.admin` 管理员 | 组长 / 交付负责人 | 管理待办与成员日常事务，不能删项目 |
| `project.member` 成员 | 开发、测试、现场实施 | 领待办、提改动、发消息 |

**原则**：owner 不超过 2 人（避免无人负责），新人一律先给 member，稳定后再升 admin。

成员离场时**不要直接删**，把状态置为离场（`left`）。历史待办和提交记录都还挂在他名下，删了会断链。

### 第 5 步：用待办分工，别用嘴分工

所有任务进「项目待办」，字段建议这样填：

| 字段 | 怎么填 |
| --- | --- |
| 标题 | 动词开头，可验收。`实现 AGV 任务改派的电量阈值判断` ✅ / `改派` ❌ |
| 优先级 | `urgent` 线上挂了 / `high` 本期必须 / `medium` 正常排期 / `low` 有空再说 |
| 标签 | 按模块打：`backend` `frontend` `edge` `docs` |
| 负责人 | **必须写一个人**。写两个人等于没人负责 |
| 描述 | 背景 + 验收标准 + 关联分支名 |

状态流转（项目里已定义好，照用）：

```
待开始 ──► 进行中 ──► 完成
   ▲          │  ▲
   └── 暂停 ◄──┘  └── 暂停
```

规矩：

- 开分支前先把待办切到**进行中**，并写清分支名
- **超过 3 天没动的进行中，必须切暂停或拆小**，否则周会看不出真实进度
- 完成前在待办下留一句"验证方式"，方便验收
- 长期任务用子待办拆，不要一个待办挂两周

### 第 6 步：网盘放"不该进 Git 的东西"

项目网盘建这套目录，和仓库形成互补：

```
00-设计与方案/     架构图、接口文档定稿、评审材料
01-现场素材/       现场照片、录屏、点位图、库区布局
02-交付物/         验收报告、操作手册、培训材料（docx/pptx/pdf 定稿）
03-数据样例/       脱敏后的订单/库存样例、日志片段
04-第三方资料/     设备厂商协议、SDK、说明书
99-归档/           过期版本，只读保留
```

判断标准一句话：**文本能 diff 的进 Git，二进制和大于 20MB 的进网盘**。

### 第 7 步：定两个会，其他都省掉

- **周会 15 分钟**：只看待办板，谁卡住、卡在哪、要不要换人
- **合入即通知**：PR 合进 `main` 后，在项目消息里发一条一句话说明（改了什么、要注意什么）

不要开会同步进度 —— 待办板就是进度。

## 2. 新人上手清单

给每个新成员发这一段，让他自己走一遍：

- [ ] 拿到仓库地址，`clone` 下来，跑通 `scripts/init-repo.*`
- [ ] 配好 `user.name` / `user.email`（用公司邮箱，别用默认值）
- [ ] 读 `README.md` 的目录结构 + `CONTRIBUTING.md` 的七条硬规则
- [ ] 进 WorkBuddy 项目，认领一个 `low` 优先级的待办练手
- [ ] 走完一次完整流程：开分支 → 提交 → PR → 评审 → 合入
- [ ] 拿到项目网盘权限，知道大文件该放哪

## 3. 常见坑（都踩过）

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| **只有一人有最新版** | 别人改完还要发压缩包 | 强制走远端，禁止用 U 盘/微信传代码 |
| **换行符打架** | 整个文件全红，实际只改了一行 | `.gitattributes` 已统一；本地 `core.autocrlf=false` |
| **大文件把仓库撑爆** | `clone` 要半小时 | 单文件 > 20MB 走 LFS 或网盘；已入库的用 `git lfs migrate` |
| **Excel 互相覆盖** | 两人改同一张表，后保存的把前一个盖了 | Excel 不做文本合并。定"一人一表"或改在线表格 |
| **文档和代码脱节** | 代码改了，文档还是老版本 | 文档改动和代码改动放同一个 PR |
| **分支活太久** | 合并时冲突几百处 | 5 天不合并就拆小；每天 `pull --rebase` |
| **待办没人认领** | 周会上互相看 | 待办必须指定负责人，无主的进 backlog 不排期 |
| **密钥泄露** | `.env` 被提交上去 | `.gitignore` + `scripts/pre-push-check.sh` 双保险；已泄露的立即轮换密钥 |

## 4. 什么时候该上自动化

等项目稳下来再考虑，别一上来就搞重流程。优先级从高到低：

1. **CI 跑测试与 lint**（每次 PR 自动跑）—— 收益最大
2. **合入 `main` 自动构建镜像 / 打 tag** —— 省手工发布
3. **每周一自动汇总待办状态发项目消息** —— 省周会准备
4. 代码覆盖率、依赖漏洞扫描 —— 有余力再说
