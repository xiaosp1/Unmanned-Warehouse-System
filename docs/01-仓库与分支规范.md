# 仓库与分支规范

## 1. 分支模型

采用**主干开发 + 短分支**，不搞 Git Flow（对 3–8 人团队过重）。

```
main ───●────●────●────●────●───►  始终可运行、可部署
         \        \        \
          feat/a   fix/b    docs/c    短分支，≤5 天
```

| 分支 | 从哪切 | 合到哪 | 命名 | 生命周期 |
| --- | --- | --- | --- | --- |
| `main` | — | — | — | 永久 |
| `feat/*` | `main` | `main` | `feat/WH-12-agv-dispatch` | ≤ 5 天 |
| `fix/*` | `main` | `main` | `fix/WH-31-inbound-conflict` | ≤ 2 天 |
| `docs/*` | `main` | `main` | `docs/collab-guide` | ≤ 3 天 |
| `hotfix/*` | `main` | `main` + tag | `hotfix/v1.2.1-null-pointer` | ≤ 1 天 |
| `release/*` | `main` | `main` | 可选，仅在有版本冻结需求时用 | 按发布节奏 |

命名规则：`<类型>/<待办号>-<3到6个英文单词>`。全小写，连字符分隔，不用中文和空格。

## 2. `main` 的保护规则

在代码平台设置里逐条落实：

- 禁止直接 push（包括管理员）
- 禁止 force push、禁止删除分支
- 合并前必须有 PR
- 至少 **1 个** approve；改 `src/shared/` 或 `deploy/` 需要 **2 个**
- CI 必须绿
- 分支必须与 `main` 同步后才能合并（"Require branches to be up to date"）
- 只允许 **squash merge**，合并后自动删源分支

## 3. 日常循环

```bash
# 每天开始
git switch main
git pull --rebase
git fetch --prune

# 开活
git switch -c feat/WH-12-agv-dispatch
# 待办状态切到「进行中」，描述里写分支名

# 开发，小步提交（每 30–60 分钟一次，每步都编译得过）
git add -p            # 逐块确认，避免把调试代码带进去
git commit            # 自动带出 .gitmessage 模板

# 提交前同步主干
git fetch origin
git rebase origin/main
# 有冲突 → 在自己分支解决 → git add . && git rebase --continue
# 搞砸了 → git rebase --abort 重来

# 自检
bash scripts/pre-push-check.sh

# 推送并提 PR
git push -u origin feat/WH-12-agv-dispatch
```

## 4. 合并策略

| 场景 | 做法 | 理由 |
| --- | --- | --- |
| 常态 | **Squash merge** | `main` 历史一条一个功能，回滚干净 |
| 长分支拆出的多个独立改动 | 逐个 PR | 评审粒度小，风险可控 |
| 紧急修复 | `hotfix/*` 直接 squash 合入，随后打 tag | 缩短故障时间 |

Squash 后的提交信息 = PR 标题，所以**PR 标题必须符合提交规范**。合并时把 PR 描述里的"为什么改"补进 commit body。

## 5. 冲突处理原则

1. **公共分支永不变基。** 只 rebase 自己的分支，`main` 只接受正向合并。
2. **冲突在自己分支解决**，不要反向合到 `main`。
3. 冲突超过 20 处，说明分支活太久了 —— 停下来评估是否拆分。
4. 二进制文件（Excel、图片、模型）冲突**不要手工选**，先确认哪份是对的，再覆盖。
5. 解决完必须**重新跑一遍自测**，冲突解决引入的 bug 最隐蔽。

## 6. 版本与发布

- 语义化版本 `vMAJOR.MINOR.PATCH`
  - `MAJOR`：对外接口/协议不兼容
  - `MINOR`：新增功能，向后兼容
  - `PATCH`：缺陷修复
- tag 打在 `main` 上，格式 `v1.2.0`
- 每个 tag 配一份 Release 说明：新增、修复、已知问题、升级注意事项
- 现场交付版本**必须**对应一个 tag，禁止用"某天的 `main`"交付

## 7. 不可回滚的操作清单

以下操作做之前，先在项目消息里说一声，至少两人知情：

- `git push --force`（仅限自己的个人分支）
- `git rebase -i` 改写已推送的提交
- 删除远端分支
- 修改 `main` 的保护规则
- 启用 / 迁移 Git LFS
- 在仓库里跑 `git filter-repo` / `git lfs migrate`
