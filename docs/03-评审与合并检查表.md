# 评审与合并检查表

评审的目标不是"找错"，是**让三个月后的自己看得懂为什么这么改**。所以只提两类意见：
**必须改**（正确性、安全、数据一致性）和**建议改**（可读性、结构）。其余不纠缠。

---

## 一、提交者自检（提 PR 前，逐条过）

### 正确性
- [ ] 本地跑通了，不是"应该能跑"
- [ ] 边界情况想过：空值、并发、超时、重复请求、设备离线
- [ ] 错误路径有处理，不是 `catch {}` 吞掉
- [ ] 涉及金额/库存/任务状态的计算，有对账或幂等保护

### 干净度
- [ ] `git diff` 里没有调试代码（`console.log`、`print`、`debugger`、注释掉的大段代码）
- [ ] 没有顺手改的无关文件（格式化整文件、改无关缩进）
- [ ] 没有提交 `.env`、密钥、真实客户数据
- [ ] 没有冲突标记 `<<<<<<<`
- [ ] 新增依赖说明了理由，且锁版本

### 可维护性
- [ ] 命名说人话（`calcAvailableSlots` 而不是 `calc2`）
- [ ] 复杂逻辑有注释说明**为什么**这么做，不是复述代码
- [ ] 公共函数/接口有文档字符串
- [ ] 配置项从配置读，不硬编码 IP、端口、库区编号

### 交付完整度
- [ ] 关联待办已更新（分支名、进度、验证方式）
- [ ] 接口变更同步了文档（`docs/` 或 OpenAPI）
- [ ] 数据库变更附了迁移脚本和回滚脚本
- [ ] PR 描述填完整，截图/录屏已贴

---

## 二、评审者关注点（按优先级）

### P0 · 必须拦下
- **数据一致性**：并发写入同一库位/同一任务，会不会覆盖
- **幂等性**：重试会不会产生重复任务、重复扣减
- **安全**：SQL 注入、越权访问、密钥硬编码、日志打印敏感信息
- **协议兼容**：改了 `src/shared` 的字段，老版本设备/前端还能不能跑
- **破坏性变更**：删字段、改语义、改默认值，有没有升级说明

### P1 · 应该提
- 错误处理是否区分了"可重试"和"不可重试"
- 日志够不够定位问题（有 traceId 吗、有上下文吗）
- 性能：循环里查库、无分页的全表扫描、N+1 查询
- 测试覆盖了核心路径没有

### P2 · 提一句就够
- 命名、拆分、重复代码
- 注释是否说清了"为什么"

### 不要提
- 纯个人风格偏好（引号、行宽），交给 linter
- "我觉得可以用另一种架构"——除非能指出当前方案的具体问题

## 三、合并前检查（合入者执行）

```
□ CI 全绿（测试 + lint + 构建）
□ 至少 1 个 approve；src/shared、deploy 需 2 个
□ CODEOWNERS 里的人已经 approve
□ 所有讨论已 resolve，没有"待确认"
□ 分支已与 main 同步（无冲突）
□ PR 标题符合 <type>(<scope>): <摘要>
□ 变更范围与 PR 描述一致（没有夹带）
□ 关联待办已挂上
```

合并动作：

1. 用 **Squash merge**
2. 把 PR 描述里"为什么改 / 怎么验的"补进 commit body
3. 删除源分支
4. 在项目消息里发一条一句话通知（改了什么、要注意什么）
5. 待办状态切「完成」

---

## 四、评审时限

| 情况 | 时限 |
| --- | --- |
| 提交者响应评审意见 | 24 小时内 |
| 评审人给结论 | 24 小时内（超时视为默认通过，但要留痕） |
| `urgent` 缺陷的 PR | 2 小时内，允许先合后补测试，但必须开待办跟进 |

> 评审卡住超过 24 小时，提交者有权在项目消息里 @ 责任人，或者换评审人。
> **不要因为等评审而让分支活着超过 5 天。**

---

## 五、有分歧怎么办

1. 先看 `docs/` 里有没有既定约定，有就按约定走
2. 没有约定 → 谁的成本更低选谁，别争论"最优"
3. 还谈不拢 → 项目负责人在 24 小时内拍板，并把这个决定补进 `docs/`
4. **不要为了通过评审而改出一个更差的方案** —— 该顶就顶，说清理由
