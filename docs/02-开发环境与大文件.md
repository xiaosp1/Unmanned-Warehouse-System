# 开发环境与大文件管理

## 1. 环境版本

团队必须对齐版本，否则"我这能跑"会变成常态。在仓库根放版本声明文件：

| 文件 | 内容 | 作用 |
| --- | --- | --- |
| `.nvmrc` | `22` | 前端 Node 版本 |
| `.python-version` | `3.11` | 后端 Python 版本 |
| `package.json` 的 `engines` | `"node": ">=22 <23"` | 安装期强制校验 |
| `requirements.txt` / `pyproject.toml` | 锁定依赖版本 | 避免依赖漂移 |

推荐做法：

- Node 用 `nvm` / `fnm`，Python 用 `uv` 或 `venv`，**不要用全局环境**
- 前端统一 `pnpm`（有 `pnpm-lock.yaml` 就只用 pnpm，别混用 npm/yarn）
- 后端依赖必须锁版本，`pip freeze` 出来的 `requirements.txt` 或带 lock 的 `pyproject.toml`

## 2. 首次配置（每人做一次）

```bash
git config --global user.name  "你的名字"
git config --global user.email "you@company.com"

# 换行交给 .gitattributes，不要依赖 autocrlf 自动转换
git config --global core.autocrlf false
git config --global core.safecrlf warn

# 中文文件名正常显示（Windows 默认会转义成 \344\275\240）
git config --global core.quotepath false

git config --global pull.rebase true
git config --global fetch.prune true
git config --global rebase.autoStash true
```

Windows 额外两条：

```powershell
# 路径过长（D:\01-DEMO\Unmanned Warehouse System\... 很容易超 260 字符）
git config --system core.longpaths true

# 国内网络加速（按需）
git config --global http.https://github.com.proxy http://127.0.0.1:7890
```

`scripts/init-repo.ps1` 已把这些写进**仓库级**配置，新人不用记。

## 3. 换行符：为什么必须靠 .gitattributes

Windows 默认 CRLF，Linux/容器是 LF。不统一会出现两种事故：

- 只改了一行，`git diff` 显示整个文件都变了 → 评审没法看
- Shell 脚本变 CRLF → 容器里报 `bad interpreter: /bin/bash^M`

本仓库的 `.gitattributes` 已经定好：

| 文件类型 | 入库 | 检出 |
| --- | --- | --- |
| 一切文本 | LF | LF |
| `*.ps1` `*.bat` `*.cmd` | LF | **CRLF**（PowerShell 需要） |
| `*.sh` | LF | LF（容器需要） |
| 二进制 | 原样 | 原样 |

**不要修改这些规则**，除非你明确知道后果并且在 PR 里说明了。

如果已经出现"全文件变更"，用这个诊断：

```bash
git diff --stat                    # 看是不是整个文件都变了
git config core.autocrlf           # 应该是 false
git ls-files --eol path/to/file    # 看该文件实际的 eol 状态
```

## 4. 文件体积：硬性上限

| 类型 | 上限 | 超了怎么办 |
| --- | --- | --- |
| 单个文本文件 | 1 MB | 拆文件 |
| 单个二进制文件 | 20 MB | Git LFS 或项目网盘 |
| 仓库总体积 | 1 GB | 清理历史 + 迁移大文件 |
| `node_modules` / `.venv` | 0（禁止入库） | 已在 `.gitignore` |

`scripts/pre-push-check.sh` 会在推送前拦下超过 20MB 的文件。

### 4.1 该放哪，一张表判断

| 内容 | 去处 | 理由 |
| --- | --- | --- |
| 源码、配置样例、SQL 迁移脚本 | **Git** | 需要 diff、需要历史 |
| 架构图（`.drawio` / `.mmd` 源文件） | **Git** | 文本格式，能 diff |
| 架构图导出的 `.png` | **网盘**（Git 里放链接） | 二进制，改一次涨一个版本 |
| 接口文档（`.md` / OpenAPI `.yaml`） | **Git** | 要和代码同 PR 改 |
| 验收报告、操作手册（`.docx` / `.pptx`） | **网盘** | 二进制，不做文本合并 |
| 现场照片、录屏 | **网盘** | 体积大 |
| 点云、地图、模型权重 | **网盘** 或 LFS | 单个动辄上百 MB |
| 脱敏数据样例（`.csv` < 5MB） | **Git** | 测试要用，需要版本 |
| 现场真实数据 | **都不进**，脱敏后取样例 | 合规 |

### 4.2 启用 Git LFS（可选）

只有在"大文件必须跟代码版本绑定"时才用（比如模型权重需要和代码版本一一对应）：

```bash
git lfs install
# 取消 .gitattributes 里对应行的注释
git add .gitattributes
git commit -m "chore: 启用 Git LFS 管理模型权重"
git push
```

注意：

- LFS 需要平台支持且**占用配额**，团队要事先确认额度
- 已经入库的大文件不会自动迁移，需要 `git lfs migrate import --include="*.onnx"`
- 迁移会改写历史，**必须全员停手、重新 clone**，属于高危操作

## 5. 密钥与配置

- 仓库里只放 `.env.example`（字段名 + 说明 + 假值）
- 真实 `.env` 在 `.gitignore` 里，每人本地一份
- 生产密钥放部署平台的密钥管理，不进任何人的电脑
- 提交前 `scripts/pre-push-check.sh` 会扫常见密钥特征（`AKID`、`sk-`、`BEGIN PRIVATE KEY` 等）
- **一旦泄露，改 `.gitignore` 没用**，必须立刻轮换密钥，再考虑清历史

## 6. 提交前自检

```bash
bash scripts/pre-push-check.sh      # Linux / Git Bash
.\scripts\pre-push-check.ps1        # Windows（如有）
```

检查项：冲突标记、超大文件、疑似密钥、调试残留（`console.log` / `print(` / `debugger`）、
`.env` 是否被跟踪、提交信息是否符合规范。
